See "Open follow-ups from the 2026-07-05 expansion" at the end for what the agents found that changes existing assumptions.**

## Purpose and shape

Catalogs external biological data sources the TaxaID ecosystem fetches from (or could fetch from), across both roles a source can play:

-   **Observation data** — the evidence side of the pipeline (sequence, image, acoustic match objects feeding TaxaLikely/TaxaMatch).
-   **Context data** — the prior side (occurrence records feeding TaxaExpect/TaxaFetch).

**One table, one row per (source, data type) pair — not a wide table with one column per data type.** A source spanning multiple roles (iNaturalist serves both image-CV scoring *and* occurrence/range data) gets one row per role rather than one row with several TRUE/FALSE cells, because the two roles genuinely differ in auth, rate limits, and even what "location" means (consumed vs. returned) -- flattening that into a single row would lose exactly the distinction that matters. Filtering `Data Type` gives you the "observation data" or "context data" view without maintaining two separate tables.

**Habitat context column, not habitat-specific sources:** this table does not catalog habitat-data sources (land-cover, WorldClim, etc. -- a genuinely different category, LLM/raster-derived in this ecosystem's `TaxaHabitat`, not fetched from a biodiversity database). Instead, the `Habitat Field?` column records whether a *given source* happens to carry a habitat-like field alongside its observations (e.g. GBIF's Darwin Core `habitat` term exists but is rarely populated) -- a data-quality note about existing sources, not a new source category.

**Every cell should be scannable at a glance.** The first draft of this table packed several distinct facts (a value, its caveat, and a citation) into single prose cells -- `Access & Auth` and `Location Metadata` were the worst offenders. Fixed by splitting those into short categorical columns and moving citations, caveats, and `[needs verification]` flags into a trailing **Notes** column. If a new row's cell starts running past a phrase or two, that's a signal to split the column or move the detail to Notes rather than let the cell grow.

**Cells are tags, not sentences.** Prefer a short noun phrase over a clause -- `Birds (some frogs/mammals)` instead of "heavily bird-skewed, though some frog/mammal recordings exist." Anything needed to justify or explain the tag (why, how confirmed, what the exact enumerated values are) goes in Notes. `[needs verification]` itself stays in the cell as a short flag; the reason it's unverified goes in Notes, not inline in the cell.

**Confidence:** entries are either (a) confirmed directly against this ecosystem's own working code (cited by function name, usually in Notes), or (b) general knowledge about the source not yet verified against a live API call or response schema, marked **[needs verification]**. Don't treat (b) entries as load-bearing for an implementation decision without checking the live API first.

## Columns

| Column | Meaning |
|----|----|
| Source | Database/service name |
| URL | Home page or API root |
| Data Type | `sequence` / `image` / `acoustic` / `occurrence` (one row per type a source provides) |
| Access Mechanism | Live API / bulk download / scrape-only |
| Auth / Rate Limit | Key or token requirement (env var name if this ecosystem already uses one), request-rate ceiling |
| Location Fields | Field name(s) that carry location, if any |
| Location Precision | Short categorical: exact coords / coords + uncertainty radius / range-check only / consumed not returned / free-text locality |
| Habitat Field? | Yes / No / Unconfirmed -- does this source carry a habitat-like field alongside the observation |
| Taxonomic Scope | Breadth and known bias, one phrase |
| Evidence Type | Vouchered specimen / expert ID / community ID / algorithmic classifier output |
| Known Issues | Short tag(s) for documented failure modes -- detail and citation go in Notes |
| License | Redistribution terms (per-record where it varies) |
| Ecosystem Integration | Package/function already using this source, or "not yet" |
| Notes | Citations, caveats, `[needs verification]` reasons, endpoint quirks -- anything that would otherwise bloat another cell |

## Open follow-ups from the 2026-07-05 expansion

Things the four research agents found that change an existing assumption or surface a real, actionable item -- not just row content:

-   **DataONE CN may not actually be sunset.** `TaxaFetch/R/dataone_occurrence_search.R:11`'s comment ("DataONE CN (cn.dataone.org) is sunset -- do not use") was contradicted by a live query this session (`cn.dataone.org/cn/v2/query/solr/?q=*:*` returned 3,358,598 records). If true, this ecosystem's DataONE pipeline currently only reaches EDI (one Member Node) and is missing \~40+ others. Worth a deliberate decision, not a silent fix -- re-verify independently before changing any code.
-   **`fetch_reference_recordings()` does not exist.** Referenced in `README.md`/`CLAUDE.md`/`NAME_CHANGE_HISTORY.md` as an existing, migrated TaxaLikely function (documentation drift noted earlier this same session); the real functions are `TaxaLikely::fetch_xc_recording_locations()` and `.xc_recording_count()`/`audit_acoustic_coverage(xc_recordings=)`. Worth fixing the stale references next time that area is touched.
-   **GTDB has a real REST API** (`api.gtdb.ecogenomic.org`) for taxon/lineage lookups -- doesn't change how `subset_local_database()` would consume GTDB (still bulk download), but corrects this doc's own earlier assumption that SILVA/MIDORI2/GTDB/Greengenes2 shared one uniform "bulk download only" shape.
-   **License conflicts worth resolving before any redistribution work**: MIDORI2's license is reported as CC-BY-NC in secondary sources (unconfirmed on the primary site) and BOLD's license is entirely unstated anywhere reachable -- both would need a direct answer (e.g. contacting BOLD support) before this ecosystem redistributes anything sourced from them, given the real Session 124 incident with eBird/Macaulay-sourced photos.
-   **Greengenes2 and GTDB both carry habitat-like fields**, but in metadata layers (`empo_0`-`empo_3` EMP-sample layer; `ncbi_isolation_source` genome-metadata TSV) that this ecosystem's current parsing (`subset_local_database()`, taxonomy-string only) doesn't reach -- the fields exist in the source's data universe but aren't currently wired to anything here.
-   **PR2 has the richest habitat-adjacent metadata of any source in this table** (ENVO-coded environment, biotic relationship, sample type, trophic mode) but is not integrated anywhere yet, despite being named as relevant to the 18S phytoplankton workflow. **Update (Session 136): PR2 is now integrated** via `TaxaLikely::subset_local_database()` -- see its row above.
-   **BOLD migrated to a new v5 API in 2024 -- not a temporary outage (Session 136, corrected from an earlier same-session finding).** The `bold` R package's `bold_seqspec()`/`bold_identify()` target BOLD's old v3/v4 API, which is now permanently retired ("BOLD Public Offline" is a retirement message, not a downtime message). The real, current API is BOLD's v5 Data Portal (`portal.boldsystems.org/api`, documented by its own public OpenAPI spec) -- confirmed fully live via a real 3-stage round trip. **`fetch_bold_reference_sequences()` is now built and shipped** directly against this API via `httr2`, no `bold` package dependency needed. **`identify_bold_sequences()` (the query/ID-engine side) has no public API to build against** -- confirmed via BOLD's complete OpenAPI paths list (20 endpoints, none for sequence identification); the "Barcode ID" tool is web-form-only under v5. See `project_bold_v5_migration_resolved` memory for the full record.
