# Response to the WERC software-release review of TaxaID

This is the repository's response to the release review recorded in
`WERCReview.docx`, whose requests are tabulated in this folder's `README.md`.
Each request is answered below with what the repository now does. It is a
record for the release, kept outside every package; it does not ship in any
built package.

## On deleting test files

The nine packages carry 174 test files (roughly 8,000 tests), run with
`devtools::test()` and by `R CMD check`. They are how several real defects were
caught during pre-publication review, and a standard R package ships its
`tests/` directory so that `R CMD check` can exercise it on any machine. We
read the request as aimed at scratch and development scripts rather than the
test suite; those scripts have been moved out of the repository. We would like
to confirm that reading with the reviewer before deleting anything under
`tests/`.

## Changes made after the review comments were incorporated

I responded to the code review in September 2026, after which test cases
with real data were applied, and feedback was sought from potential users at
the Global eDNA Conference at the end of October. Responding to users
required some additional changes, so this section records what changed
since, separately from the responses above, which stand as written. All
additions were subject to USGS code-review standards.

### Scope of the change

- Export surface: **223** exported objects (218 functions and 5 data objects)
  across the nine packages, checked against the packages themselves by the
  test suite.
- **16 exported functions were added** and **10 were removed**, a net
  reduction in surface rather than growth. The removals were the larger part
  of the work: several were functions no caller reached.
- Test files: this response stated **174** when it was written. The tree now
  holds **217**, 43 more. That figure was accurate at submission and is left
  as written above.

### Functions added

`add_unreferenced_prior_mass`, `annotate_reference_support`,
`check_lineage_agreement`, `classify_sample_identity`,
`estimate_kernel_priors_from_counts`, `estimate_sequence_matrix_size`,
`fetch_gbif_occurrence_counts`, `fetch_inat_occurrence_counts`,
`flag_backbone_conflicts`, `flag_failed_libraries`, `flag_hopped_detections`,

`review_sample_identity`, `screen_assignments`.

### Functions removed, and why

The LLM-Bayesian assignment route was **removed on 2026-10-26**:
`TaxaAssign::assign_taxa_llm()`, together with the LLM-priors path, the
`known_absent`/`detection_prob` absence-suppression mechanism that existed
only on that route, and the two pipeline wrappers `run_bayesian_pipeline()`
and `run_llm_pipeline()`.

It was removed because it was measured and did not earn its place: on the
CalIntertidal data it was no better than a flat prior (8.38 flat against 7.92
and 8.45 for two variants), and on a Great Lakes 12S dataset it matched the
occurrence-based priors from TaxaExpect rather than beating them. Nothing in
the ecosystem called it. A package is easier to review and to trust with one
documented assignment route than with two, one of which was not better.

The LLM *review* routes are untouched and remain: `review_assignments()`,
`review_sample_identity()`, `review_spatial_context()`,
`build_habitat_lookup()`, `suggest_unreferenced_species()` and
`review_flagged_accessions()`. These report probabilities and verdicts
alongside an assignment; they never make the assignment.

Also removed, each because no caller reached it: `build_iucn_scheme()`,
`build_scheme_prompt()`, `parse_scheme_response()`, `correct_training_bias()`,
`verify_local_corroborations()`, `model_cache_info()`. `fetch_inat_occurrences()`
was renamed `fetch_inat_occurrence_counts()` to say what it returns.

### Documentation corrections

Several documentation sentences were found to state behaviour the code does
not have, and were corrected rather than carried into the release. The ones
worth naming, because each told a user something that would have changed what
they did:

- `TaxaTools` stated that `prompt_api()` retries a failed LLM chunk
  automatically. It does not; it warns, records the failed chunk indices, and
  stops only if every chunk failed. Retry is implemented elsewhere in the
  ecosystem, which made the claim especially easy to believe.
- `TaxaLikely::fetch_ncbi_reference_sequences()` documented its reference
  cache as defaulting to `tempdir()`, clearing on restart. The default is a
  persistent per-user cache, so results from an earlier session are reused
  unless the cache is cleared.
- `TaxaFlag::screen_assignments()` described its own resolution rules
  incorrectly, and each is named here rather than counted: rule R4 reads the
  geography column at the scale the caller did *not* pass, not the study-wide
  one; a poor sequence fit is not a sequence vote unless `likelihood_support`
  is present; the occurrence fallback chain begins at
  `consensus_has_occurrence_record` and includes `consensus_plausibility`;
  evaluability is decided per row, not per column; rule R7's confirm test
  needs the sequence vote, a decidable stability and a decidable
  `prior_driven`, so it is not a rule that reads only what every gated row
  carries; and `resolution_counts` reports `evaluated` and `n_evaluable`
  beside `n_rows`. A reader reconciling a resolution against the help would
  have reached the wrong rule.
- `TaxaAssign`'s own contributor notes stated that the package default
  `consensus_method` is `"lca"`. All three functions that take the argument
  default to the weighted form; `"lca"` is the opt-in. Only the function
  definitions were right: the README, the `@details`, the contributor notes, a
  workflow snippet and the ecosystem vignette all carried the old default, and
  all were corrected.
- Every argument whose default is deliberately *not* the production setting
  now says why it is the default, rather than leaving a reader to infer that
  the default is the recommended value. Three of these were reviewed as
  needing a production value named instead: nothing anywhere in this
  repository sets `max_per_genus` or `irreducible_only`, and the one
  checked-in workflow template passes `seed = 1L`. No production value is
  claimed for any of them, because none is established.
- `TaxaLikely`'s reference-cache key now records which direction its two
  failure modes run in -- a key too coarse serves a stale fetch, a key too
  fine refetches needlessly -- and warns against substituting a hand-rolled
  digest, which does not stay stable across versions of the hashing package.

### Behaviour corrected

- `TaxaAssign::add_slash_taxon()` now breaks ties in `primary_taxon` by byte
  order, the rule the rest of the package already used. Equal-evidence ties
  decide a substantial share of calls, so without it the column depended on
  the machine's collation and the same input could name a different taxon
  elsewhere. The rule breaks exact ties only, and that was measured rather
  than assumed: across four real datasets -- 55,671 Point Conception
  observations carrying two or more hypotheses, plus Mugu, and two Great
  Lakes runs -- there were 55 exactly equal top-two posteriors, 54 of them in
  the Point Conception table and one in Mugu, and not one pair separated by
  less than 1e-8. The smallest non-zero gap anywhere was 2.6e-05, more than
  three orders of magnitude above 1e-8, the largest tolerance probed. A
  tolerance large enough to ever bind here, 1e-4, would instead have merged 14
  Point Conception observations whose posteriors genuinely differ. Top-two gaps are bimodal, exactly zero or far from it, so no
  rounding tolerance was introduced; a tolerance would have had nothing to
  catch and could only have merged distinct results.
- `TaxaExpect::condition_evidence_on_habitat()` now reports a weight that
  habitat conditioning reduced to zero, as a `habitat_zeroed` column and a
  warning. The existing `habitat_floored` column could not fire at the
  default floor of zero, so a zeroed weight previously had no column that
  named it.
- `TaxaMatch::review_flagged_accessions(on_unreviewed = )` now lets the caller decide what
  happens when accessions in scope come back with no review verdict, and
  records the unreviewed accessions on the result either way. Previously a
  review that failed outright was indistinguishable in the output from one
  that found nothing wrong, because both left `NA`.
- `TaxaLikely::audit_barcode_coverage()` now records when its census was
  taken, as `census_date` and `census_time`. A coverage census describes a reference database at a moment, and
  without a timestamp a saved census could not be told from a current one.
- `TaxaFlag::screen_assignments()`'s `resolution_counts` now carries
  `evaluated` and `n_evaluable` beside `n_rows`. A rule that fired on no rows
  and a rule that could not be evaluated at all both read `0` before, which
  are opposite findings: the first says the rule was asked and said no, the
  second says it was never asked. `evaluated` answers whether the rule's
  inputs were present anywhere, and `n_evaluable` counts the rows that both
  reached the rule and carried its inputs. `evaluated` is deliberately not
  defined as `n_evaluable > 0`, which would make five of the eight rules
  report "not evaluable" on an input holding a single `verify_range` row.
- `TaxaFlag::screen_assignments()` decides evaluability for rules R1, R4, R6
  and R7 per row rather than per column. A column that exists but is empty on
  a given row cannot support a verdict on that row, so counting it as
  evaluable reinstated the same zero-versus-not-asked confusion one level
  down. R7 is the subtle case and was found by an independent reader of this
  branch: it resolves every row it reaches, so it looks like a rule that needs
  nothing, but its only discriminating question is confirmed-or-upheld and
  that needs the sequence vote, a decidable stability and a decidable
  `prior_driven`. Without them every row comes back "upheld" by default rather
  than by test, which is the same defect the column exists to expose. The run
  message now prints the denominator beside the count, as `R1 = 0 (0 asked)`,
  because a bare zero could not be told from a rule no row reached.
- `TaxaLikely::audit_barcode_coverage()`'s `census_date` is the local date.
  `as.Date()` on a `POSIXct` converts in UTC, so without a time zone the
  census read as tomorrow's date for the whole local evening, on any machine
  west of UTC. One limit is documented rather than claimed away, because it
  was measured: on a machine whose time zone the operating system cannot
  resolve, R falls back to UTC regardless of what is passed, and the case
  is not reliably detectable from `Sys.timezone()`: where `TZ` names a zone
  the system does not know it returns that unknown name rather than `NA`,
  though it can return `NA` where `TZ` is unset and the zone cannot be
  determined, so neither value is a dependable signal. `census_time` is exact
  on any machine and is the value to compare two censuses on.
- `TaxaTools::fill_higher_ranks()` accepts a `cache_dir` to reuse backbone
  answers across calls. It defaults to no caching, so existing callers are
  unaffected; the package does not choose a cache location on the user's
  behalf.
- `TaxaLikely::fetch_ncbi_reference_sequences()` gained a documented account
  of how it detects and removes cross-lineage (homonym) contamination in a
  fetched reference set, and of when that rule deliberately does nothing.
- `TaxaFlag::screen_assignments()` was checked on 2026-11-10 against a
  conventional match object -- a candidate list per observation with a score
  for each, never processed by TaxaID -- and three things were corrected.
  (1) `poor_fit_col` and `best_identity_rank_col` accept `NULL`, meaning the
  table carries no absolute-fit evidence. Before, a caller without
  TaxaLikely's absolute fit had to invent the column, and the honest invention
  (`NA`) was read as a good fit, so the screen reported
  `I1: good fit, geography plausible: keep name` on evidence it had never
  seen. With `NULL` the rules that read the fit report themselves as not
  evaluable and the reason text says the fit was not supplied. A non-`NULL`
  name must still exist as a column, so a typo is still an error.
  (2) A row whose only evidence is the review itself now reports
  `flag_resolution` `"not_assessed"` with an `NA` consistency score, on every
  branch including exclusions. Where the sequence vote is absent and no
  occurrence-record column is present, the occurrence vote speaks for the
  reviewer's geography verdict and the habitat vote for its habitat
  probability: two votes read off one instrument. Counting them as independent
  gave such a row the maximum consistency score on no evidence outside the
  review, and could stamp an exclusion `"confirmed"` on the reviewer's own two
  verdicts. This is the same double count the posterior is deliberately kept
  out of the vote to avoid. A row carrying either axis of real evidence is
  unaffected, so no table built by the TaxaID pipeline changes.
  (3) A comment in the resolution step asserted that such a row would fall
  below the two-vote gate and be reported as not assessed. It did not: the
  gate was reached on those two votes. The comment now describes the code, and
  (2) is what makes the behaviour it described true.

### Capabilities added in response to user feedback

Two additions came directly from the user feedback described above, and both
are reported here because each is visible to someone already using the
packages.

- `TaxaFlag::screen_assignments()` now resolves its own advice against all the
  evidence on a row, reporting `flag_resolution`, a plain-language
  `flag_resolution_basis` naming which inputs produced it, and
  `flag_consistency_score`. Users were combining the LLM review columns, which
  read easily because they are words, without the better-calibrated posterior
  quantities sitting beside them. The resolution is deterministic, runs after
  the LLM verdicts rather than influencing them, and introduces no new
  statistic: it votes on sequence support, occurrence records with geography,
  and habitat, and will not produce a score from fewer than two of the three.
  The occurrence prior is deliberately NOT given a vote, because the posterior
  already integrates it; it is reported as a caveat instead, so that a prior
  which is strong only because a database is well sampled cannot inflate
  confidence twice.

  **Behaviour change for existing callers:** this is on by default, so every
  current caller of `screen_assignments()` receives three additional columns.
  Harmless unless a caller selects that output by position or asserts a fixed
  set of columns.

- `TaxaAssign::posterior_consensus(reference_snapshot =)` labels a consensus
  with the reference state it was computed against, as both an attribute and a
  per-row column, and `update_prior_from_consensus()` warns when labelled and
  unlabelled rows are combined. A new vignette section documents updating
  assignments after new reference data without rerunning the whole workflow,
  including when the likelihood model must be retrained. Users asked for this;
  the computational pieces already existed, so what was added is the record
  that keeps a partial update honest. The risk it addresses is a result that is
  half old rows and half recomputed rows with nothing to say which is which.
  It defaults to off and changes nothing for callers that do not set it.

### Documentation structure

One correction is worth recording because it affected what the documentation
said rather than how it read. A new section in
`fetch_ncbi_reference_sequences()` had been placed inside the return-value
block, which moved two paragraphs -- including the full account of what the
function returns in dry-run mode -- out of the return value and into that
section. The return value no longer documented a supported mode. It was found
by comparing the generated LLM-context files against a written prediction of
what should have changed, and corrected before release.

### Documentation and packaging

- The ten READMEs were reviewed by the maintainer and corrected. Three places
  still described an LLM-Bayesian assignment workflow that was removed in
  October: TaxaAssign's README offered it as one of three workflows, the
  ecosystem vignette listed "LLM priors" as a prior source, and TaxaTools'
  README named it as an LLM step to compare across models. A user following
  any of them would have looked for a function that is not there. The identity
  rule table in TaxaFlag's README stated two configurable arguments as if they
  were fixed, and now names them.
- The repository URL is marked provisional throughout, with every file holding
  it listed in `usgs_release_review/REPO_URL_SWAP.md`, so the USGS-issued URL
  can be substituted in one verifiable pass.
- TaxaFetch's 28 test files had never run under `R CMD check`: the package had
  no `tests/testthat.R`, so its check reported no errors because nothing was
  tested. A driver was added. On its first CI run it immediately surfaced a
  test that calls GBIF live on every build, which is now skipped there through
  the mechanism the other packages already used.
- The review correspondence no longer ships to users. The reviewer comments
  and our responses stay in the repository as the record of the review, but
  they were installed inside each package -- 763 KB across the nine -- and are
  now excluded from the build. Stale planning documents, session notes and
  one-off validation scripts were removed from the repository. One kind of
  development material still ships, deliberately: `TaxaLikely`'s
  `inst/review_function_inputs.R`, a runnable input for each exported
  function, because 15 of that package's help pages cite a numbered section of
  it and a user following one of those pointers needs the file present.
- Two PDFs of published papers shipped inside `TaxaFetch`, in every tarball
  and in a public repository. They are licensed CC BY-NC 3.0, which does not
  permit redistribution, and the package is CC0. Build-excluding them would
  have left the repository copies, so they were removed outright. Three
  scripts read them. Two now report that no PDF is bundled, explain how to
  supply one, and skip the section; the third has since been removed. A
  separate build-exclude pattern for a `pdfs` directory is unrelated and was
  kept: it is anchored to a top-level developer scratch directory that
  `download_literature_pdfs()` creates, and it never covered the shipped
  files.
- Four development scripts no longer ship: a staged PDF-pipeline test, a
  harness that calls every exported function in sequence, a hand-run remote
  BLAST field test, and a single-site reference-screening driver. They stay in
  the repository.
- A review-input script that shipped, `TaxaFetch`'s, had its billed-LLM flag
  set to `TRUE`, while its own header four lines above stated that all such
  flags default to `FALSE`. A reviewer running the file top to bottom made
  real, billed Anthropic calls, and because the file shipped, that reached
  users rather than staying inside the repository. The flag was corrected, and
  the script itself has since been removed: it also called
  `fetch_dataone_eml()`, which no package exports any more, and no `TaxaFetch`
  help page pointed at it, so nothing was relying on it.
- A licence and provenance sweep of every other non-code file found no further
  rights problem. The images are the maintainer's own, and no object anywhere
  in the nine packages carries record-level occurrence data: the two files
  derived from GBIF hold aggregated counts per taxon, grid cell and habitat,
  with no record identifiers, per-record coordinates or collectors.

### What the checks did not catch

Three limits in the verification itself are worth recording, because each one
meant a green result that did not mean what it appeared to.

- A green check once rested on documentation that had not been rebuilt. The
  generated LLM-context files are compared against their committed copies, but
  the comparison is built from the *installed* help database. With stale
  `man/*.Rd` on disk, the guard compared stale against stale and passed; three
  help files were affected. A guard that cannot fail is not a guard, so the
  expected differences are now pre-registered before the comparison runs, and
  the regeneration happens after installing the branch rather than before.
- A failing test in continuous integration reported only its test name. The
  step now prints each failure, error and skip with its message and diff, so a
  red build can be read without reproducing it locally. The existing pass and
  skip guards were left as they were.
- One package's pass and skip counts depend on a third-party service. The
  habitat tests fetch two small public bathymetry tiles, so the same code
  reports different skip counts depending on whether `gis.ngdc.noaa.gov`
  answers. This reconciled a pass-count discrepancy between two runs that had
  no other explanation. Three further tests there used a conditional skip on
  an empty result, which would have reported success had the result become
  empty for any reason; each measured as never firing and is now an assertion
  that the result is non-empty.
